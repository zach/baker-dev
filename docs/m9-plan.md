# M9 plan: the docs, the examples, and the reference harness

Draft for review. Spec §10 (the M9 row) is the requirement; spec §4 ("Personal, experiment,
and scratch layers"), §5 ("Evaluating text"), D41/D42 (the readiness panels), and
`docs/background/iteration-backgrounder.md` §6 (use cases, and the live-ops lessons) say
what the docs must teach. The open questions at the end change the plan. Once they are
answered, the decisions go into `docs/decisions.md`, and this file is deleted when M9 is
done.

## Scope

From the M9 row:

- `README.md`, with the one-line-constant pitch up front;
- `docs/language.md`, a guide to the language: data, the preprocessor, packs, and script;
- `docs/cookbook.md`, patterns, with a live-ops section;
- `examples/`: config, scripting, objects, tasks, remote-console, live-ops overlay, and
  `harness-imgui`.

Done when:

1. A reader can go from zero to a working tweak in under five minutes of reading.
2. The cookbook's live-ops section covers environment boundaries, version history,
   rollback, and personal and experiment layers.
3. The harness pushes a personal `local` layer by the convention in spec §4.

Not in M9: loop statistics and the edit journal (M10), new library features. A gap the
docs expose goes in `docs/decisions.md` and to the owner, not into M9.

## What exists

- `README.md` (206 lines) describes M5 and lists features through M7; it predates the
  cache, packs, shapes, and the M8 numbers.
- `docs/cookbook.md` (57 lines): groups, personal layers, experiments.
- `docs/script-reference.md`: generated by `moira::reference()`; a test fails when it
  drifts. It stays generated, and `language.md` links to it.
- `examples/one_line_tweak` and `examples/calculator`, each run by CTest against expected
  output.

## Design

### 1. README

- First screen: what Moira is in two sentences, then the one-line tweak, before and after.
- **A five-minute path** (criterion 1): build, a 10-line `default.dta`, the tweak, a
  `Config` with one layer, edit the file, `reload()`, see the value change. About 600 words
  and 40 lines of code to a working tweak, at a reading pace of 200 words a minute.
- Then: what else is there, one paragraph and a link each (lookup, layers and write-back,
  script, objects and messages, tasks, the cache, packs, shapes), the build table, status,
  and the numbers measured so far. The long feature list moves into the docs it
  summarizes. (Q3.)

### 2. `docs/language.md`

The language as an author meets it, not the C++ API:

1. Data: atoms, strings, arrays, commands, properties, variables; comments; how tags and
   lookup work.
2. The preprocessor: `#include`, `#include_opt`, `#require`, `#merge`, conditionals,
   defines and macros, `#autorun`.
3. Packs and levels, and the one-way rule.
4. Shapes: declarations, types, metadata, what a shape governs.
5. Script: evaluation (laziness, no special forms), variables and scoping, `{func}`,
   objects and `{class}`, messages, tasks, `check` and the demand report.
6. Errors: what a located error says and how to read the script stack.

### 3. `docs/cookbook.md`

Keep the three sections; add:

- **Live ops** (criterion 2): overlays as layers; **environment boundaries** (dev, QA,
  live as separate layer stacks or directories, `freeze()` and `live_layers` for what a
  shipped build may change); **version history** (overlays as files in version control,
  named by date, and `snapshot()` beside a repro); **rollback** (`remove_layer`, and why
  it leaves no trace); tests (`check` and shape validation in CI before an overlay ships);
  personal and experiment layers (the existing sections, linked).
- Tweaks in practice, reload callbacks (migrate or punt), the binary cache in a build step
  (`moira_bake`, `cache_dir`), harness packs (`#require`, levels), a developer console
  over `eval`, and recorded repro scripts.

### 4. Examples

Each is a small program with a CTest run against expected output, as the two that exist
are. Proposed:

| Example | Shows | Test |
|---|---|---|
| `config` | layers, provenance, reload, write-back to a temp copy | output match |
| `scripting` | `func`, natives, `eval`, `check` | output match |
| `objects` | `Object<T>`, methods, properties, `{class}`, a typed message | output match |
| `tasks` | a C++ coroutine and the script tasks, ticked | output match |
| `remote-console` | a TCP listener feeding `eval`, under 100 lines (spec §5) | Q2 |
| `live-ops` | an overlay pushed, its effect, a rollback, `freeze()` with `live_layers` | output match |
| `harness-imgui` | Q1 | Q1 |

`one_line_tweak` stays (the README's first example); `calculator` stays or folds into
`scripting`.

### 5. `harness-imgui`

From the M9 row and D42: panels generated from the tweak registry and shapes (range
sliders, kinds such as `color`), an `eval` console, provenance on hover, save-to-source
through write-back, and three readiness panels: **Loop** (recent reload records as stage
bars, edit-to-see time when the host supplies origins), **Layers** (the stack with enable
toggles, each layer's effect, a promote button showing refusals in place), and
**Snapshots** (capture A, capture B, flip). It pushes `local/<user>.dta` with
`{.optional = true}` (criterion 3). How it is built and tested is Q1.

## Budget

No core code is planned. Estimated sizes: README ~250 lines, `language.md` ~600,
`cookbook.md` ~350, examples ~900 lines of C++ and data, `harness-imgui` ~700.

## Open questions

**Answered 2026-10-12 (D87):** Q1–Q4, each as recommended.

**Q1. How `harness-imgui` is built and tested.**
- **Recommended.** Dear ImGui fetched at a pinned release (as EASTL is), with GLFW and
  OpenGL 3 for the window, behind `MOIRA_BUILD_HARNESS` (off by default). The panels are
  plain functions over a `Config`, `TweakRegistry`, and `Context`, so CI runs them
  headless: ImGui with no backend, a few frames, assertions on what changed.
- **Panels only.** Ship the panel code against ImGui's API, with no window or backend; a
  host drops it into its own ImGui setup. Less to build, nothing to run on screen.
- **Separate repository.** Keep the harness outside this repository.

**Q2. The remote console's platforms.**
- **Recommended.** Portable: BSD sockets with a small Winsock shim, so it builds and is
  tested on every CI platform, MSVC included; its test connects over loopback, sends three
  commands, and checks the replies.
- **POSIX only.** Simpler; not built on Windows.

**Q3. The README's shape.**
- **Recommended.** Short: the pitch, the five-minute path, one paragraph per feature with
  links, the build table, and the measured numbers. The full feature list moves into
  `language.md` and the cookbook.
- **Keep it long.** Update the current README in place, adding M6–M8b.

**Q4. Testing the code in the docs.**
- **Recommended.** The README's five-minute path is also a CTest program
  (`examples/quickstart`), and a script checks that the README's code block matches it
  line for line, so the path cannot rot.
- **Every block.** Extract and compile every C++ block in the docs. Thorough, but most
  blocks are fragments.
- **None.** Review by hand.
