## 1. What the code says

- **A view borrows from the tree.** `std::string_view` points at a `String` node, `ListView<V>`
  at a field's `Array` (`packed_` reserved for a packed `V[]`, D279), `Curve` at the points'
  nodes, a nested struct inline; `Symbol`s are interned pointers. A packed table must own
  what its views point at: a pool of bytes beside the array of structs.
- **A merge shares what it did not change.** `merge_into` hands back the lower array's
  nodes where the upper has nothing for them (`same_nodes`, D75), so after a reload the
  arrays a table was built from are the same objects unless a record under them changed.
  Pointer identity of a table's source arrays is the "records changed" test.
- **`commit` swaps the root.** `Config::Impl::commit` builds the merged tree, runs the
  validators, binds the tweaks and tells the subscribers; `root()` is a `Ref<Array>` a reader
  holds across the swap. Tables swap in the same step.
- **The cache loads in place with one pass** (`cache.cpp`'s `load`): every record is walked
  once, symbols interned from the image's table into their slots, block and line fields
  filled. The header has no section directory (`root`, `meta`, `symbols` fields; version 8).
- **Shipping keeps no view names:** `ViewInfo::name` is empty, `kShapeDigest` is not. A
  table is found by digest.
- **The host kit knows the game's views** (`CommandHooks::views`), and `check` compares
  them with the contract set; the kit's commands run on the game's own binary, where the
  generated structs exist. `baker_bake` is a library tool with no view struct.
- **The assembly test** (`tests/codegen/check_tweak_read.cmake`) compiles one function to
  assembly and counts its instructions, excluding calls and branches.
- **Nothing in the stacks is `(@view)` yet;** `examples/content-tables` and the test
  projects are the corpus.

## 2. Design note

### 2.1 The transforms, by path class

| Transform | Class | How often |
|---|---|---|
| a table read, `(*t)[i]`, `t->index_of(key)` | hot | per read: one indexed load; a hash probe |
| building a table from the merged tree | load | per merge, per registered table whose source arrays changed |
| loading a table from the image | load | once per table, in the image's one pass |
| writing the image | tool | `bake` |

A Config with no registered table builds none and pays one empty-vector test per commit.
A stack with no `(@view)` keyed shape generates no `register_tables` body.

### 2.2 `Table<T>`: an array of structs, a pool, and three indices

```cpp
template <class T>
class Table {           // one block from the Config's allocator; refcounted (Ref<const Table<T>>)
    std::span<const T> rows;          // records in the merged tree's order, grouped by parent
    const std::byte* pool;            // strings, packed list elements, curve points
    // indices, built with the rows:
    //   keys:    (hash of the record's key, or of parent/key for a * shape) -> row; aliases too
    //   ids:     RecordId -> row, sorted
    //   parents: (parent key -> [first, last)) for a * shape
};
```

- `operator[](i)` is an indexed load, unchecked; `at(i)` returns `Expected<const T&>`.
- `index_of(Symbol key)` for a shape without `*` in its `@at`; `index_of(std::string_view
  path)` and `index_of(const Path&)` for the path below the table (`kestrel.jab`);
  `index_of(RecordId)`. A key that is a record's alias resolves to it, as the merge does
  (D286). `children_of(Symbol parent)` is a contiguous `IndexRange`.
- Rows are `T` as the generated header declares it, so a game's code is one load away from
  a field. Strings and lists point into the pool: a `ListView<V>` with `packed_ = 1` reads
  `V[]` directly, which W1 reserved.

### 2.3 Building: the generated reader, then a relocation

The library cannot know `T`; the generated code knows it and nothing about tables. The seam
is a per-view **fix-up list**, generated beside the struct: a `constexpr` array of
`{offset, kind}` for every member that points outside the struct (`string_view`, `ListView`,
`Curve`, `Symbol`, and the nested structs' members, offsets summed), with the element kind
of each list. With it the library builds, writes and loads tables type-erased:

- **In memory:** for each record the shape governs, in the merged tree's order,
  `ViewReader<T>::read` fills a `T` that borrows from the tree; the builder then walks the
  fix-up list and copies each borrowed string, list and curve into the pool, pointing the
  member at the copy. Packed list elements are converted once (`ListView<V>::at` per
  element) into `V[]`. One pass over the records, one allocation per table.
- **Where the records are:** the generated struct carries its shape's `@at` path
  (`kAt`, segments with `*`), so the builder finds the governing arrays as `shape::check`
  does, without the shape set at run time.
- **Literals only** (spec, C4): a `{command}`, `$variable` or `[property]` in a view field
  is reported at the field, located, and the member reads as its default (§4 Q2); a field
  marked `(@view no)` is never read into the table.

### 2.4 Registering and reading

`baker::add_table<T>(cfg)` registers before the load: the digest, `sizeof(T)`, the fix-up
list, `kAt`, and a build callback the template instantiates. `baker::table<T>(cfg)` returns
`Ref<const Table<T>>` for the digest, as of the last commit. The generated `tables.hpp`
(§4 Q3) has `register_tables(Config&)` calling `add_table` for every viewed `(@keyed)`
shape. The Config keeps `Vec<TableSlot>`: the spec, the `Ref` of the current build, and the
source arrays it was built from.

### 2.5 Rebuilding: in `commit`, by identity

After the merged tree is built and before the validators run, each slot whose source arrays
are not the same objects as before is rebuilt from the new tree and its `Ref` replaced; a
reader holding the old `Ref` keeps it (the spec's "swap it in with the tree"). A live edit
(`apply_edits`) is a commit too. An index is stable while the table's set of records is
unchanged: the rows are in tree order, and a merge keeps the lower array's order.

### 2.6 The image: version 9, a section directory

`game.datb` is one cache file whose header gains a directory: after the symbol table, a
count and `{kind, offset, bytes, digest}` per section, where kind is a contract layer's tree
(its `meta` beside it, as a per-layer cache has), a table, or the stack's freshness record.
The format version becomes 9; a per-layer `.datb` is a version-9 file with one tree section,
so one loader reads both. The container's endianness, pointer-size and hash rules hold.

A table section is the rows and the pool as bytes, with its digest, `sizeof(T)`, the
fix-up list's hash, and the indices. The loader fixes up in the image's pass: a `Symbol`
member from the image's symbol table, as a tree node is; a `string_view`, list or curve
pointer from its offset into the pool. A section whose digest, size or fix-up hash differs
from the registered table's is skipped with a located warning, and that table is built from
the tree.

### 2.7 Who bakes (§4 Q1)

The image is written by the game's own binary, through the host kit: `game bake
--baker-stack game.datb` loads the contract stack as the game registers its tables, builds
them with the compiler's own layout, and writes the image. `baker_bake` has no view struct,
and simulating the compiler's layout from the shape (the sizes and alignments of `int8` to
`double`, `bool`, `Symbol`, `string_view`, `ListView`, `Curve`, nested structs) is ABI
knowledge the library should not carry. `bake` runs in a shipping build too: it reads text
and writes a file, which shipping allows (`format` does the same), so the shipping example
can bake its own image in its test.

### 2.8 What this plan changes in the spec

- The image is written by the kit's `bake` on the game's binary, not `baker_bake --stack`
  (§2.7).
- `register_tables` lives in a generated `tables.hpp`, so `views.hpp` stays the light
  header (§4 Q3).
- A `{command}` in a view field reads as the default with a located error, rather than
  failing the build (§4 Q2).
- The image is a container of its own (`MOIRA.IMG1`) holding each layer's cache as
  `write_cache` writes it and each table's block with a relocation list, rather than a
  cache format version 9 with a section directory: the cache's format and loader are
  untouched, and a per-layer cache stays what it was (D294).

## 3. Steps

Each step runs `tools/local_matrix.sh` and clang-tidy before its commit, and records its
result in its D-entry (D291 onward).

1. **The fix-up lists and `kAt`.** The generator writes `kFixups` and `kAt` into each view
   struct; `ListView`'s packed mode. Golden headers updated. Tests: the lists match the
   members; a packed list reads.
2. **`Table<T>` in memory.** `<baker/table.hpp>`, the builder, the three indices,
   `add_table`/`table`, the slots in the Config, rebuild in `commit` by identity. Tests:
   build, read by index, key, path, ID and parent; an alias resolves; stable indices across a
   reload; a held `Ref` outlives a rebuild; a `{command}` reported; the alloc gate.
3. **`register_tables`** in the generated `tables.hpp`; the views project and the host test
   game register; `check` reports a registered table with no shape.
4. **The image.** Version 9 with the section directory; `write_image` and the loader's table
   sections; `ConfigOptions::stack_image`; the kit's `bake`; a mismatched section's fallback.
   Tests: a round trip, a shipping load, the fallback, the alloc gate.
5. **The assembly test and the benchmarks.** `tests/codegen/table_read.cpp`: a read by index
   and by key, checked as the tweak read is; `bench_view` rows for a table read against
   `find_float`; the no-cost rows.
6. **The example, the docs and the record.** `examples/content-tables` bakes and loads the
   image in its shipping test; `docs/language.md` (Tables), `docs/cookbook.md`,
   `docs/tools.md`; the gaps rows (44: a table read is the per-frame path); the changelog
   lines in the D-entry.
